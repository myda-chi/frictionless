# Frictionless demo repo (D1)

A small Java project with a pre-baked, multi-file AI-authored change - never generated live, per
the build plan's own rule (§6, D1).

## Use it

```
./demo/reset-demo.sh
```

Regenerates `demo/repo/` (git-ignored, safe to delete any time): a clean commit of the pre-change
code, with the AI's change applied on top as an **uncommitted** working-tree diff. Open
`demo/repo` in IntelliJ IDEA with Frictionless in working-tree mode (the default) to run the demo.

Run it again any time to reset to the exact same starting point - that's the whole point.

## What the change contains

`transfer-demo` is a toy payments service (`Account`, `FxRateProvider`, `TransferService`). The
base commit has full test coverage for `Account` and `TransferService.transfer`. The AI's change
(`ai-change.patch`) does three things at once, giving all three ledger buckets in one small diff:

| Method | What changed | Bucket |
|---|---|---|
| `TransferService.transfer` | Refactored to call a new `moveFunds` helper - behaviour unchanged | 🟢 Proven (existing tests still pass) |
| `Account.debit` | "Allows" a small overdraft buffer for pending holds | 🟡 Behaviour changed (`AccountTest.debitRejectsAmountsLargerThanBalance` now fails) |
| `TransferService.applyFxMargin` | Simplified while extracting `moveFunds` - the 1% margin was silently dropped | 🔴 Unverified (no test reaches it - nothing catches the regression) |

`applyFxMargin` is the same method named in specification.md §3.6's narration example, on purpose.

## Editing the demo

Never hand-edit `demo/repo/` - it is fully regenerated by `reset-demo.sh` every time. To change
the demo:

1. Edit the base project under `demo/source/`.
2. Edit the AI's change under `demo/source/`, then regenerate the patch:
   ```
   cp -R demo/source /tmp/demo-base && (cd /tmp/demo-base && git init -q && git add -A && git commit -qm base)
   # apply your edits to /tmp/demo-base, then:
   (cd /tmp/demo-base && git diff) > demo/ai-change.patch
   ```
3. Run `./demo/reset-demo.sh` and confirm it still applies cleanly and produces the intended
   pass/fail split (`javac` + a JUnit console launcher, or just open it in IntelliJ and run the
   tests).
